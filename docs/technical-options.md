## 開発の前提

- 開発者はTypeScriptとReactの経験があり、モバイルアプリ開発は初めて。
- 開発者は趣味のWeb開発でTailwindをよく使っている。
- 開発者はZod・Valibotの両方の使用経験がある。
- 普段のパッケージ管理にはpnpmを使用しており、本プロジェクトもpnpmを採用する。具体的なバージョンとExpo・Metro・Storybookに必要な設定は初期構築前に確認する。
- 手元の検証用実機はiPhone。開発中はiPhone実機とAndroidエミュレーターを使用する。公開前にはAndroid実機でも写真の取り込み・記録の保存・指操作などの主要操作を確認する。Android実機の確保方法は未決定。エミュレーターの準備は[Expo公式資料](https://docs.expo.dev/workflow/android-studio-emulator/)を参照する。
- iPhone・Android向け、端末内保存、オフライン利用。アカウント・サーバーは不要。
- 月々の維持費はストア登録費などを除き原則ゼロ。
- スクラップの見た目と、壊れない端末内の記録を優先する。

## 個別に確認した採用方針

- React Compilerを初期構築で導入・有効化する方針を確認済み。[Expoの公式手順](https://docs.expo.dev/guides/react-compiler/)と[Reactの導入資料](https://react.dev/learn/react-compiler/installation)を参照し、採用するExpo・Reactに対応した依存の版と設定を確定する。NativeWind・Reanimated・Workletsとの併用、MetroとブラウザStorybook（Vite）の各変換設定・コンパイル結果を検証する。Expo側の有効化だけでStorybookにも適用済みとは扱わない。LintはOxlintを維持し、公式資料のESLint設定例をそのまま追加しない。Compilerは1.0.0で固定して有効化済み。Metro（Android/iOS）とStorybook Viteの変換を検証し、実機での実行は未確認。
- Expoアプリを1つのプロジェクトとして構成し、Storybook・Vitestも同じプロジェクト内で管理する。アプリ・UI・ロジックを別パッケージへ分割せず、フォルダで整理する。基本のディレクトリ構成は後述の方針に従う。単一プロジェクトとして初期構築済み。製品機能は後続段階で実装する。
- 実機開発はDevelopment Buildを採用し、手元のMacでExpo CLIとXcode・Android Studioを使ってビルドする。[公式の導入方針](https://docs.expo.dev/develop/development-builds/introduction/)に沿って`expo-dev-client`を導入する。クラウドビルド契約は開発の前提にしない。Development Buildの依存とapp configは構築済み。Xcode・Android SDK・署名と実機でのビルドは未確認。通常のTypeScript変更とネイティブ依存・設定変更で必要な再ビルドを区別する。
- Lintには[Oxlint](https://oxc.rs/docs/guide/usage/linter.html)、整形には[Oxfmt](https://oxc.rs/docs/guide/usage/formatter.html)、Gitフックの管理には[Lefthook](https://lefthook.dev/configuration/)を採用する。ESLint・Prettier・Huskyは標準構成に追加しない。導入済みの版・ルール・フック設定を引き継ぐ。具体的なコマンドはAGENTS.mdと開発手順を参照する。
- 記録の保存には`expo-sqlite`を使う。
- ORMは追加せず、SQLで読み書きする。画面からSQLを直接呼ばず、保存・取得を担当する小さな関数にまとめる。
- 写真の画像本体はDBに埋め込まず、端末内のファイルとして保存する。
- 写真のファイル操作には`expo-file-system`を採用する。写真の永続領域を基準にした相対パスをDBに保持する構成とする。別のファイル操作ライブラリは併用しない。
- 写真の縮小・圧縮には`expo-image-manipulator`を採用する。加工結果を`expo-file-system`で永続領域へ保存する。スクラップの傾きは表示で付け、演出のために画像本体を回転・再圧縮しない。
- 写真選択には`expo-image-picker`を採用する。OSの写真選択画面で複数の静止画を選び、加工と保存はそれぞれの専用モジュールへ渡す。カメラ撮影・動画選択は使わず、不要な権限を求めない構成を確認する。
- フォーム入力や表示設定などのUI状態はReact標準のstate・reducer・Contextで始め、Zustand・Redux等は追加しない。
- TanStack QueryはMVPに導入しない。SQLiteの取得結果は画面表示時や保存・削除等の確定後に読み直す。取得状態・エラー処理・画面を離れた後の反映防止を小さな共通処理にまとめ、独自の汎用キャッシュ基盤は作らない。
- 訪問履歴はReact Native標準の`FlatList`で始める。写真一覧は2列程度で写真ごとに幅・位置・傾き・余白を変える方針へ変更したため、従来の「写真一覧もFlatListで始める」判断は再検討する。標準の`numColumns`による同じ高さの行では、可変幅と空白を詰める要件を満たさない。写真一覧の描画・仮想化方式と追加ライブラリの採否は未決定で、HTMLの配置処理をそのまま数千枚の本実装へ流用しない。
- 画面遷移はExpo Routerを採用し、Stackを中心とした単純な構成にする。日本・世界の切り替えは地図画面内で扱い、別の画面遷移方式を重ねない。
- 木製地図の描画は`react-native-svg`を採用する。境界データを同梱してオフラインで県・国を選択できる構成とし、無地の濃い茶色の木製ボード、薄い木色の地形、控えめなピンで描く（木の色味を残し、木目模様は再現しない）。境界データの出典と利用条件、拡大縮小・移動の方式は別途選定する。
- 地図・写真の指操作には`react-native-gesture-handler`を採用する。ピンチ・パン・タップ等の関係を制御し、地図と写真で共通利用する。
- 地図・写真の指操作に追従する描画更新には`react-native-reanimated`を採用し、必要な`react-native-worklets`も使用する。対応するExpo・React Nativeとのバージョン整合は初期構築前に確認する。装飾的なアニメーション追加を目的にしない。
- 日付入力はOS標準の日付選択を利用し、`@react-native-community/datetimepicker`を採用する。紙のフォームから選択画面を開き、独自カレンダーは実装しない。
- UIはReact Nativeの基本部品を組み合わせて独自実装する。UIキットは導入しない。
- 操作用アイコンにはLucideの`lucide-react-native`を採用する。[公式の導入方法](https://lucide.dev/guide/react-native/getting-started)に従い、採用済みの`react-native-svg`を利用する。必要なアイコンを個別にインポートし、大きさ・色・線幅を共通化する。具体的なバージョンはExpoが対応するSVGの版との整合を確認して定める。
- スタイルにはNativeWindを採用する。通常の余白・色・文字・配置に使い、写真ごとの計算値はstyle、指操作中の表示更新はReanimatedで扱う。採用版とExpo・ブラウザStorybookの適合は別途確認する。
- 独自UIの確認用にStorybookを開発環境へ組み込む。ブラウザ版とネイティブ版の別入口を構築済み。公式の入口差し替え方式を採用し、実機検証の残件は段階1一覧に記載する。

## プロジェクト内の構成（方針決定）

```text
src/
  app/         # 画面の入口・画面遷移
  features/
    map/       # 地図・ピン
    records/   # 訪問履歴・入力・アルバム
  components/  # 共通の紙・ボタンなど
  storage/     # SQLite・ファイル操作
```

- 機能ごとの処理はfeatures、共通UIはcomponents、永続化の具体的な処理はstorageへ置く。画面の入口であるappへ処理を集中させない。
- VitestのテストとStorybookの表示例は、対象の部品・処理の近くに置く。画面遷移用のapp内には置かず、必要な表示部品・処理をfeatures等へ切り出す。
- ブラウザStorybookの設定やネイティブ機能の代替処理は同じプロジェクトで管理する。具体的な設定ファイルや配置は初期構築時に確認する。
- このツリーは製品全体の構成方針。現在はsrc/appとsrc/componentsを作成済みで、未実装の機能フォルダは先行作成しない。

## 第一候補

React Native + Expo + TypeScriptを採用方針とする。Reactの経験を生かし、両OSで画面と記録処理を共通化する。WebのReactと異なるレイアウト・写真権限・ファイル保存・アプリ配布の学習は必要。

## 依存ライブラリの方針（決定事項）

- できるだけ依存ライブラリを増やさず、必要な箇所だけ採用する。
- React・React Native・Expoの標準機能で満たせる場合は、それを優先する。
- 追加時には、満たす要件、標準機能では不足する理由、両OSへの対応、保守状況を確認する。既存ライブラリと役割が重なるものは避ける。
- 安全性や端末固有の処理が重要な部分は、依存削減のために無理に自作しない。OSの写真選択などは既存モジュールを利用する。

## シンプルに保つ境界

バックアップ関連の検討はMVPから外し、[将来候補の保留資料](future-backup.md)へ移した。暗号化ZIP・外部書き出し・外部JSON検証のための依存は現在の構成に含めない。

### 独自UIとStorybook

#### スタイルの書き方の選定結果

今回のUIは共通の一種類のスクラップテーマで、写真のサイズ・傾きはTypeScriptの計算結果を表示に渡す。色・余白・文字サイズ・素材を共通定義する。[React Native標準のStyleSheet](https://reactnative.dev/docs/stylesheet)と比較したうえで、開発者のTailwind習熟度と日常のUI調整のしやすさを踏まえNativeWindの採用を確認済み。

[NativeWind](https://www.nativewind.dev/docs)でTailwind形式を使う。UIの見た目は独自実装し、スタイルの書きやすさのために採用する。

#### 今回のアプリでの比較

| 判断材料           | StyleSheet                                         | NativeWind                                                                                                                                            |
| ------------------ | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 独自UI             | 共通部品とスタイルで表現できる                     | 共通部品とユーティリティクラスで同様に表現できる。既製UIを使うことにはならない                                                                        |
| スクラップの世界観 | 色・余白・書体・素材をTypeScriptの共通定義で揃える | Tailwindテーマと素材・部品で揃える。テーマが一種類であることだけで不要とは判断しない                                                                  |
| 見た目の調整       | JSXの部品とスタイル定義を往復する                  | 余白や配置をJSX上で変更でき、Tailwindに慣れている場合は調整が速くなる可能性がある                                                                     |
| 写真の自動配置     | 計算した寸法・傾きをstyleへ渡す                    | 通常の見た目はclassName、計算した寸法・傾きはstyleへ渡す併用ができる。写真ごとの任意の数値をクラス名の動的生成だけで表そうとしない                    |
| 指操作への追従     | Reanimatedで必要なtransformを更新                  | 同様にReanimatedで更新する。NativeWindだけでジェスチャーや配置計算を実現するわけではない                                                              |
| ブラウザStorybook  | React Native Webで表示し、ネイティブとの差を確認   | それに加えTailwindのCSS生成・読込・クラス探索・JSX設定をVite側でも整える必要がある                                                                    |
| 依存・設定         | 追加のスタイル処理系なし                           | NativeWindと対応するTailwind・CSS連携・ビルド設定が加わる。一部のネイティブ依存は採用済みのReanimated等と役割が重なるため、全てが新規追加とは数えない |

公式の[インストール手順](https://www.nativewind.dev/docs/getting-started/installation)と[他のバンドラーへの組み込み条件](https://www.nativewind.dev/docs/guides/other-bundlers)を確認済み。NativeWind採用時はExpo/Metroだけでなく、日常の確認環境であるブラウザStorybookでも同じクラスが反映されることを導入時に確認する。NativeWindとTailwindの対応世代は版によって異なり、Webの最新Tailwind設定をそのまま転用できると考えない。

開発者のTailwind習熟度と、Storybookを含む初期設定の負担を比較した。日常のUI調整を簡単にする目的で、必要な依存として採用する。

通常の余白・色・文字・並びはNativeWind、写真配置の計算結果はstyle、指操作中の変化はReanimatedに分ける方針を確認済み。NativeWindの採用版とExpo SDK・ブラウザStorybookの適合は別途確認し、未検証の組み合わせやプレリリース版を暗黙に採用しない。スタイル用ライブラリは一つに絞り、クラス結合・バリアント管理用の追加ライブラリは最初から導入しない。

#### 決定事項

- 木製地図、画鋲、紙、マスキングテープ、履歴や入力部品は、共通の色・余白・書体・素材を使って独自に構成する。OS機能への接続まで無理に自作する意味ではなく、日付選択は採用済みの標準UIを使う。
- Storybookは開発用の確認環境として採用する。製品に必要な依存と、開発のための依存を分けて管理する。
- Storybookはブラウザ版とネイティブ版を用意し、日常の表示確認はブラウザを主にする。色・余白・紙やテープの質感・写真配置・各表示状態の調整のために、毎回実機やシミュレーターを起動する運用にはしない。
- ネイティブ側は、フォント・文字サイズ・読み上げ・ジェスチャー・OS固有の表示など、ブラウザとの相違が問題になる部分を必要なタイミングで確認する用途とする。

#### 組み込み案（具体方式は未確定）

- [React Native Storybook公式](https://storybookjs.github.io/react-native/docs/intro/getting-started/)はExpoに対応し、起動入口を切り替える構成を推奨している。アプリ内にStorybook画面を常設せず、開発時に別の入口で開く方式を候補とする。
- 製品ビルドではStorybookのコード・stories・開発用操作を含めない。環境変数の条件分岐だけで安全と判断せず、採用バージョンの公式構成と実際のバンドルで確認する。
- ブラウザ側の候補は[Storybook for React Native Web（Vite）](https://storybook.js.org/docs/get-started/frameworks/react-native-web-vite)。実際に製品で使うReact Native部品をReact Native Webで表示し、ブラウザ確認用に別のHTML部品を二重実装しない。採用するExpo・React・Storybookに対応した依存バージョンと具体設定は初期構築前に確定する。
- 最初の対象は、紙の背景、テープ付き写真、訪問履歴項目、交通手段表示、入力項目、主要画面。部品は必要な共通単位に絞り、汎用UIフレームワークは自作しない。
- 写真あり・なし、長文、縦長・横長写真、大きな文字などの状態をサンプルデータで確認する。配置情報は固定し、Storyを開くたびに写真の傾き等を再抽選しない。
- Storyから実データを操作しない。部品は表示データと操作関数を受け取り、SQLiteやファイルへの直接依存を避ける構成を検討する。
- アドオンは必要なものだけを採用する。ブラウザ版を動かすための開発依存は許容するが、外部ホスティング・有料サービス・永続化用ライブラリを無条件に追加しない。
- SQLite・ファイル操作・OSの日付選択などは、ブラウザの表示確認に必要な範囲でスタブや差し替えを使う。DB・画像保存がブラウザで実動作する構成には広げない。ブラウザの表示確認だけで端末上の機能検証が完了したとは扱わない。

### 日付入力の方式とモジュール候補

今回必要なのは過去の訪問日と任意の終了日を選ぶこと。予定管理・イベント表示を備えるカレンダーは不要。紙のフォームの日付欄を押したとき、OS標準の日付選択を使う方針を確認済み。独自カレンダーは作らない。

OS標準を使う場合の候補は、[community datetimepicker](https://docs.expo.dev/versions/latest/sdk/date-time-picker/)と[Expo UIのDateTimePicker](https://docs.expo.dev/versions/latest/sdk/ui/drop-in-replacements/datetimepicker/)。前者は日付入力に用途を絞れる。後者は別のUIモジュールを含める選択になるため、日付のためだけに追加する妥当性を検討する。両方は導入せず、対応SDKと必要な表示形式を確認して一つを選ぶ。

比較後、日付入力に用途を絞る`@react-native-community/datetimepicker`の採用を確認済み。`@expo/ui`はこの目的では追加しない。

### 地図・写真の指操作の選定結果

地図ではタップ選択・ピンチ拡大縮小・ドラッグ移動、写真ではピンチ拡大・拡大中の移動・前後写真へのスワイプが必要。拡大中の移動と写真切り替えを区別し、タップや画面の戻る操作と競合させない設計が必要。

- [React Native標準のPanResponder](https://reactnative.dev/docs/panresponder)でも基本的な複数タッチを扱えるが、指の距離や中心、操作の組み合わせを組み立てる範囲が増える。
- [react-native-gesture-handler](https://docs.swmansion.com/react-native-gesture-handler/)は、ピンチ・パン等の認識と操作同士の関係を扱える。地図と写真で共通利用する方針で採用を確認済み。
- 写真専用のズーム・ギャラリーライブラリを追加する前に、地図と写真で共通の操作基盤を使う案を優先する。
- 描画の追従には、ジェスチャーの採用とは別に検討したうえでReanimatedを採用する。採用するExpo対応バージョンと操作方式の整合は別途確認する。

#### 指に追従する描画の選定結果

- [React Native標準のAnimated](https://reactnative.dev/docs/animations)はtransform等をネイティブ側で更新できる。追加依存を抑える選択肢だが、複数の指の中心位置・倍率・移動範囲を組み合わせる処理の実装方法を確認する必要がある。
- [Reanimated](https://docs.swmansion.com/react-native-reanimated/docs/about/)はUIスレッドでジェスチャーに応じた計算と描画更新を扱う。[Gesture Handlerの公式資料](https://docs.swmansion.com/react-native-gesture-handler/docs/fundamentals/getting-started/)でもUIスレッドでの操作処理に推奨されている。
- 現在のReanimated 4系は`react-native-worklets`も必要で、対応するReact Native・Expoとの組み合わせを選ぶ。一ライブラリだけの追加とは数えない。
- 地図と写真のピンチ・移動を共通に実現する目的でReanimatedを推奨し、必要なWorkletsを含めた構成の採用をユーザーが確認済み。装飾のためにアニメーションを増やす目的ではない。
- 操作中の倍率や座標をReactのstateで毎フレーム更新する構成は避け、DBへの保持等は操作終了後に必要な範囲で行う設計を検討する。

### SQLiteの取得結果とTanStack Queryの検討結果

- アプリの要件から判断する。React標準のUI状態管理を選んだことは、TanStack Queryの採否を意味しない。
- [Query Functionsの公式資料](https://tanstack.com/query/latest/docs/framework/react/guides/query-functions)によると、Promiseを返す取得関数を使えるため、SQLiteの非同期読み取りにも適用できる。サーバー通信がないことだけを理由に不要とは判断しない。
- 地図の訪問状態・場所の履歴・アルバムを、保存や削除後に更新するキャッシュ管理をまとめられる。取得中・失敗時の状態も共通化できる。
- 一方、クエリキー・更新後の無効化等を設計する必要がある。導入だけでDB更新の検知や画面間の整合性が自動で保証されるわけではない。
- 採用時は[Network Mode](https://tanstack.com/query/latest/docs/framework/react/guides/network-mode)を確認し、SQLite処理が通信状態に左右されない`always`を候補とする。データの正本はSQLiteで、Queryキャッシュの永続化やオフライン用の追加パッケージを重ねない方針を提案する。
- React標準によるUI状態管理とは役割が違うが、今回のMVPでは導入しない方針を確認済み。

#### 今回必要な読み取りと更新

| 画面・操作             | 必要な内容                   | Queryなしの場合の案                        |
| ---------------------- | ---------------------------- | ------------------------------------------ |
| 地図                   | 訪問済みの場所の状態を取得   | 初回表示・再フォーカス時等に読み直す       |
| 場所の履歴             | 選んだ県・国の訪問記録を取得 | 場所ID単位で取得し、保存・削除後に読み直す |
| 訪問アルバム・写真一覧 | 一件の訪問と写真情報を取得   | 訪問ID単位で取得し、編集保存後に読み直す   |
| 入力・編集             | 未保存の編集内容を保持       | React標準の画面内の状態。Query採用時も同様 |

現在の仕様には、サーバー同期、定期ポーリング、楽観的更新、複数ユーザー間の変更反映は不要。TanStack Queryを追加する主な価値は、ローカルの非同期取得状態と画面間の再取得を統一できること。

Queryなしでも、画面内の取得中・失敗・結果、再取得の契機、離れた画面の取得結果を反映しない制御は必要。小さな取得フックと保存処理の窓口にまとめ、独自の汎用キャッシュ基盤やイベント基盤を作らない方針を提案する。単に依存の数を減らすためにQuery相当の仕組みを自作するなら、TanStack Queryを使う方が適切。

現行MVPでは必須性が低いと判断し、ユーザーと確認のうえで導入しない方針を決めた。保存・削除後の表示更新が複雑になると分かった場合に再評価する。

ファイル操作は`expo-file-system`に統一し、写真の永続保存と削除を扱う。

### 保存構成

- 画像データはファイルとして保存し、DBには写真の識別子・相対パス・順序・寸法・配置情報などを持たせる案。

- 地図の道路や施設検索は不要。既存仕様の県・国選択とピンに合わせて描画方式を選ぶ。
- 課金、クラウド同期、アカウント、分析基盤を将来のためだけに追加しない。

## テスト方針（決定）

- 自動テストは、日付の判定、削除対象の判定、写真配置の安定性など、データ保護や整合性に関わる処理を中心に書く。
- Storybookでは、紙・木目・ピンの質感、文字量や写真枚数による表示を確認する。
- 実機では、写真選択、記録の保存、指操作、処理途中の終了からの復旧を確認する。純粋な関数のテストだけでOS連携や復旧が保証されたとは扱わない。
- テスト実行には[Vitest](https://vitest.dev/guide/)を採用する。Jest・jest-expoは使わない。導入済みVitest 5.1.0と既存テストを引き継ぐ。製品ロジックのテストケースは後続の実装に合わせて追加する。
- 日付判定・写真配置などのロジックを、React Native・Expoのネイティブモジュールを直接読み込まずにテストできる構成にする。ファイル・DB操作を伴う処理は、小さな操作関数を差し替えて失敗時の分岐や呼び出し順を検証する。汎用的な抽象化基盤は追加しない。
- Vitestで差し替えた処理のテストは、実際のSQLite・ファイル操作の動作確認の代わりにはしない。これらは両OSで別途確認する。モジュール差し替えについては[Vitest公式資料](https://vitest.dev/guide/mocking/modules)を参照。

## 開発ハーネス（Codex cloud対応を目標にする）

### 決定事項

- ハーネスは品質チェックの自動化に加え、AIエージェントが仕様に従って開発・検証する環境を含め、Codex cloudでの利用を目指す。
- 意思決定は人が行う。AIは合意済みの仕様・構成・作業範囲に沿って実装・検証・PR準備を担当し、仕様や設計方針を独断で確定・変更しない。判断が必要な論点は選択肢・推奨案・影響を整理して人へ確認する。合意内の通常の実装詳細や修正は自律的に進め、細部ごとの承認を増やさない。
- レビュー・マージは人が担当する。AIはPRに変更内容・検証結果・実機確認などの未実施項目を明記する。AIの実装開始は、従来どおりユーザーの明示的な許可後とする。
- pnpm・Oxlint・Oxfmt・Vitest・Lefthookを採用する。既存の導入を引き継いでおり、版はpackage.jsonとロックファイルを参照する。
- CIはGitHub Actionsを採用し、PRの共通チェックをマージ前の必須条件とする。手元・Codex cloud・CIで共通の`pnpm check`を実行し、Lint・整形確認・型チェック・Vitestをまとめて確認する方針。スクリプトとワークフローは構築済み。リモートCIとマージ保護設定の適用は未確認。
- ブラウザ版StorybookのビルドもPRの必須チェックとする。共通の`pnpm check`とは別のチェックとしてCIで実行する。ビルド成功は、画面の読み込み・設定上の問題の検出に使い、見た目の正しさやネイティブ動作の検証済みという意味にはしない。`pnpm build-storybook`をCIに追加済み。必須チェック設定は未確認。
- 依存方向の違反を自動検査し、共通チェックとCIに含める。共通UIからSQLite・ファイル操作を直接呼ばないこと、日付判定・写真配置等の計算処理からネイティブ機能を直接呼ばないことを最初の対象とする。導入済みのscripts/check-dependencies.mjsを引き継ぐ。
- 再現用の架空の記録と小さな画像をリポジトリで管理し、Storybookとテストで共用する。写真なし・長い日記・縦横の写真が混在する記録などを含め、個人の実際の記録や写真は使わない。数千枚規模の確認用データは必要時に生成し、大量の画像をリポジトリへ追加しない。具体的なデータ形式・生成方法は未決定。
- ローカル・Codex cloud共通のAI作業の完了条件は、変更に応じたテストの追加・更新、`pnpm check`とブラウザStorybookビルドの成功、仕様に影響する変更に対応した関連ドキュメントの更新とする。実機確認などの未実施の検証は完了報告に明記し、自動チェックの成功を実機検証済み・公開準備完了とは扱わない。まだ実行環境を構築していない段階では、これらを実行済みとして報告しない。
- Lefthookのコミット時チェックはステージ済みファイルのLint・整形確認、プッシュ時チェックは全体の`pnpm check`とする。PRのCIでも同じ`pnpm check`を実行する。フックは検出した問題で処理を止め、自動修正・自動ステージは行わない。修正用コマンドは別に用意する。対応拡張子の絞り込みや設定ファイル変更時の検査範囲は初期構築時に具体化する。

### 検討案・未決定事項

- [OpenAI公式のクラウド環境資料](https://learn.chatgpt.com/docs/environments/cloud-environments)では、環境の準備・テスト・公開と、リポジトリ内のスキルを利用する方法が案内されている。個人端末のスキルは自動同期されない。

- [AGENTS.mdの公式資料](https://learn.chatgpt.com/docs/agent-configuration/agents-md)を基に、リポジトリで共有できる簡潔な作業ルールを設計する。AGENTS.mdを作成済み。

## 写真一覧の描画候補（第一候補は確認済み、採用確定前）

- 訪問履歴は従来どおりFlatListを使う。写真一覧は可変幅で規則的に見えない2列程度の配置が必要となったため、別途方式を検討する。
- [FlashList v2のmasonry配置](https://shopify.github.io/flash-list/docs/guides/masonry/)を候補として調査した。異なる高さと列の占有幅を扱う機能がある。ただし、今回の自由度のある幅・位置・傾きと、再表示・追加削除時の安定性をそのまま満たすと未検証で断定しない。
- 写真一覧はFlashListを第一候補とする方針を確認済み。今回の見た目と安定性を再現できることを検証してから、採用を確定する。
- 写真の順序を変えるoptimizeItemArrangementは既定で有効とされているため、追加順を維持する要件に合わせて無効化等を検討する。写真の順序・配置情報をセル内部の一時状態に依存させない。
- 具体的なバージョン、Expo・ブラウザStorybookとの適合、寸法・回転後の余白、写真数が多い場合の描画・仮想化を検証する。Phase2でユーザー確認後に2.0.2を採用・固定し、ブラウザStorybookで縦横混在と2,000枚の仮想化を確認した。セル内の幅と傾きを変える構成とし、実機性能と最終的な配置の評価は残す。

## バージョン互換性の調査と採用結果

- [Expo SDKの公式対応表](https://docs.expo.dev/versions/latest/)ではSDK 58にReact Native 0.88、SDK 57にReact Native 0.86が対応している。Expoの版とReact Nativeの版を独立に最新版へ揃えない。
- [NativeWindの公式導入資料](https://www.nativewind.dev/docs/getting-started/installation)は安定版4.2.7についてExpo SDK 57対応を明記し、Tailwind CSS 3の構成を案内している。v5は別のRC版として案内されている。SDK 58との組み合わせはこの記述だけでは確認できず、非対応と断定もしない。
- Expo SDK 57・NativeWind 4.2.7・Tailwind CSS 3を初期構築の第一候補とする方針を確認済み。この組み合わせを採用し、直接依存の版とロックファイルを固定した。公式SDK対応表・配布metadata・実際の変換とブラウザ表示を確認した。ネイティブ表示は未確認。
- [ブラウザStorybook](https://storybook.js.org/docs/get-started/frameworks/react-native-web-vite)はReact Native WebとViteを使う。[NativeWindの他バンドラー向け資料](https://www.nativewind.dev/docs/guides/other-bundlers)はMetroを公式対応とし、他バンドラーではJSXランタイム等の設定を必要としている。最小の共通部品を使ってネイティブとStorybookの両方にスタイルが反映され、静的ビルドが通ることを確認するまで、組み合わせを検証済みとしない。
- Oxfmtを使う方針に従い、NativeWindの導入例にあるPrettier用プラグインはそのまま追加しない。

## 地図データの候補（未採用）

- 世界地図は[Natural EarthのAdmin 0 Countries](https://www.naturalearthdata.com/downloads/10m-cultural-vectors/10m-admin-0-countries/)を候補として調査した。[利用条件](https://www.naturalearthdata.com/about/terms-of-use/)では地図データはパブリックドメインとされ、加工・商用利用が認められている。
- Natural Earthの地物区分はアプリの195か国と一致しない。国マスターとの対応、小国・離島の形状、境界の扱いを確認してから採用を判断する。データを読み込むだけで195か国が選べるとは扱わない。
- 日本地図は[国土数値情報の行政区域データ（2026年版）](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N03-2026.html)を候補として調査した。提供元は都道府県名・行政区域コードを含むGeoJSON等を提供し、当該版の使用許諾条件をCC BY 4.0と表示している。出典・加工表示等の条件を採用時に確認する。市区町村の境界を都道府県単位にまとめ、表示用に軽量化する加工方法とデータ容量は未検証。
- 実際の地理データに基づく形と県境・国境を使い、細かな海岸線などを適度に簡略化して表示する方針を確認済み。県・国が欠けず、拡大して選べることを条件とする。境界線の質感の細部は優先せず、具体的な簡略化の程度は実データの選択性と描画性能を見て調整する。場所の固定IDと表示用形状を分離し、将来の地図差し替えで記録を失わない構成とする。
