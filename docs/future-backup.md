# 将来候補：バックアップと引き継ぎ

## 現在の位置付け

バックアップ・復元・機種変更時の引き継ぎはMVPから除外する。地図にピンを留め、端末内の写真と日記を振り返る体験を優先する。以前の「機種変更で引き継げることをMVP必須とする」判断を変更した。

以下は除外前の検討内容を退避した参考資料であり、MVPの仕様・依存関係・検証項目ではない。将来の提供や互換性を約束するものではなく、着手時に必要性・仕様・ライブラリを再確認する。バックアップだけのために選んだreact-native-zip-archive・expo-sharing・ValibotはMVPへ導入しない。

## 以前の機能方針（保留）

- 公開に固定の期限は設けず、記録と引き継ぎの品質を確認してから公開する。
- スマートフォンを買い替えても、記録と写真を新端末で使い続けられることをMVPの要件とする。端末変更で記録が失われると、アプリを使い続ける価値が弱いという理由で、以前の判断を変更した。
- 機種変更時は、旧端末で写真を含むバックアップファイルを作成し、新端末で読み込む手動の引き継ぎ方式をMVPに採用する。
- MVPではアカウント登録を不要とする。記録は端末内に保存し、機種変更時はバックアップファイルで移す。
- バックアップファイルはiPhoneとAndroidの間でも読み込めるようにする。
- 公開済みの旧版アプリが作成したバックアップは、更新後のアプリでも復元できるようにする。未対応の新しい形式は読み込みを中止してアプリの更新を案内し、既存記録は変更しない。
- 訪問記録に追加した写真はアプリ内にコピーし、そのコピーをバックアップファイルにも含める。
- バックアップファイルには、訪問記録がない場所の「行った／行っていない」の状態も含める。
- 表示設定はバックアップに含めない。新端末では日本地図の全体表示と初回チュートリアルから始める。
- バックアップファイルの読み込み時に端末内の記録があれば、利用者に確認してから、バックアップの内容に置き換える。既存データとの統合はMVPでは行わない。
- 復元時はバックアップ全体を読み取り・検証した後、現在とバックアップそれぞれの記録件数・写真枚数を比較表示し、置き換えの最終確認を行う。確認前に既存データを変更しない。
- 写真と日記を含むバックアップファイルはパスワードで保護する。読み込み時にパスワードを要求する。アカウントがないため、パスワードを忘れた場合の再発行はできない。
- バックアップ作成のたびにパスワードと確認用パスワードを入力し、一致を確認する。アプリ内への永続保存・次回の自動入力は行わない。以前と同じパスワードの使用は許可する。
- バックアップファイルを作成するとき、利用者がOS標準メニューから保存先・移動先を選ぶ。
- バックアップは設定画面から手動で作成する。MVPでは定期的なリマインダー通知を設けない。
- バックアップファイルの読み込みは設定画面からいつでも行える。
- 初回起動時のチュートリアルで、端末内保存と機種変更前の手動バックアップを案内する。
- パスワード違いや破損などでバックアップを読み込めない場合、端末内の既存記録を変更しない。
- バックアップ内の一部の写真・記録が壊れている場合も、読み込み全体を中止して既存データを維持する。部分的な復元はMVPでは行わない。
- 将来有料機能を設ける場合、iPhoneとAndroid間で購入状態をどう扱うか。バックアップファイルは記録を移すが、ストアでの購入状態を引き継ぐとは限らない。
- 将来、ストア内課金を導入する場合、記録のバックアップと購入権利の復元は別の問題として扱う。

## 以前のデータ設計（保留）

- 形式はAES暗号化ZIP、アーカイブ処理はreact-native-zip-archiveを使う方針。ZIP内の記録データはJSONとし、写真は画像ファイルとしてまとめる方針を確認済み。
- JSONには記録・ピン・写真の順序と配置情報、および引き継ぎ形式のバージョンを持たせる。内部DBのテーブル構造と分けて形式を管理し、検証後にDBへ取り込む。SQLiteファイルそのものを引き継ぎ形式にはしない。
- バックアップ対象は、訪問状態、確定済みの訪問記録、交通手段、写真、写真の順序と配置情報。写真がないピンも含む。
- 前回開いた日本・世界の地図、チュートリアルの表示状態などの表示設定はバックアップに含めない。新端末では初期設定とし、日本地図の全体表示から始め、チュートリアルを表示する。
- 作成時点で整合する内容をまとめる。作成中の編集が混じらない制御方法は別途設計する。
- 写真の取り込み・記録保存・バックアップ作成・復元の処理中は画面移動・二重操作・キャンセルを止め、進行状況を表示する。バックアップ作成中も記録を編集できないようにする。OSによる中断・終了時の回復は別途設計する。
- JSONの構造はValibotで検証し、画像ファイルの存在・識別子の重複・参照関係は別に確認する。
- データ形式にバージョンを付け、写真は相対的なファイル名で対応付ける。元の記録・写真の識別子と配置情報を引き継ぐ。
- 公開済みの旧版アプリが作成したバックアップ形式との後方互換性を維持する。必要に応じて旧形式を検証してから現行形式へ変換し、復元する。未対応の新しい形式は読み込みを中止してアプリの更新を案内し、既存記録は変更しない。形式更新時は公開済み旧形式の復元をテストする。
- パスワード保護、破損検出、ファイル数・容量・パスの検証を行う。アーカイブ内のパスを無条件に端末の保存先として使わない。
- 作成時は毎回パスワードを確認用と合わせて2回入力し、一致した場合に処理を開始する。パスワードは処理に必要な間だけ扱い、DB・設定・ログなどへ永続保存しない。次回の自動入力は行わず、同じパスワードの再使用は許可する。
- 復元は作業用領域で全体を検証してから、既存データの置き換えを確定する案。読み込み中に既存データを逐次消して置き換えない。
- 全体の読み取り・検証に成功したら、現在とバックアップそれぞれの記録件数・写真枚数を比較表示し、置き換えの最終確認を行う。確認前に既存データを変更しない。確認待ちは処理中の操作制限と区別し、置き換えを取りやめられるようにする。
- 復元途中の終了にも備え、旧データと新データの切り替え・再開時の回復方法を設計する。既存の記録を壊さないことを優先する。
- AES暗号化ZIPとreact-native-zip-archiveの採用方針は確認済み。採用バージョンと具体的なAPI・暗号化設定、大容量処理の方式は未確定。独自暗号は作らず、写真全体をメモリに載せない方式を検討する。

## 以前の技術比較（保留）

### バックアップの保存先選択・読み込み（書き出しは決定、読み込みは検討中）

- アーカイブ生成はreact-native-zip-archive、アプリ内のファイル操作はexpo-file-systemという分担を維持する。
- 外部保存への書き出しは[expo-sharing](https://docs.expo.dev/versions/latest/sdk/sharing/)でOS標準のメニューを開き、ファイル保存先や移動先を利用者が選ぶ方式を採用する。用途は自分のバックアップの持ち出しで、地図や日記の公開・他人への共有機能を追加するものではない。
- 保存先の選択は共有シートからの保存で満たす方針を確認済み。OS・利用できる保存アプリにより表示内容が違うため、同じ保存ダイアログを両OSで必ず出せるとは扱わない。
- 復元ファイルの選択は、[expo-file-systemのpickFileAsync](https://docs.expo.dev/versions/latest/sdk/filesystem/)を先に検討する。採用SDKでの両OS対応、選択後の読み取り権限、作業用コピーを確認し、これで足りるならexpo-document-pickerは追加しない。
- 外部保存用メニューを閉じただけで、バックアップが端末外へ確実に保存されたとは判断しない。利用者に示す完了状態と、作業用ZIPを削除する時点を設計する。

### JSONの検証の選定結果

バックアップのJSONは端末外から読み込むため、TypeScriptの型や型アサーションだけで正しいデータとは判断しない。`JSON.parse`後の値を未検証として扱い、DBを置き換える前に検証する。

- 手書きの検証関数なら追加依存は不要。ただし、記録・写真・交通手段・配置情報・形式バージョンの入れ子構造について、必須項目と型、エラーの扱いを継続して保守する必要がある。
- [Valibot](https://valibot.dev/guides/parse-data/)を使ってデータ構造を実行時に検証し、TypeScriptの型もスキーマから導出する。バックアップの構造と形式バージョンごとの検証を明示する。
- スキーマ検証に加え、参照する画像ファイルの存在、識別子の重複、場所と訪問の関係、配置情報の妥当性、展開先の安全性は別途確認する。形式・容量の制限と検証順序を設計し、大きなJSONを無制限に処理しない。
- フォーム全体の管理ライブラリは、この目的では追加しない。フォームの入力状態はReactで管理する。

#### ZodとValibotの比較

ZodとTypeScript向けのValibotを比較し、Valibotを採用する方針を確認済み。以下は選定時の比較資料。

| 判断材料         | Zod                                                            | Valibot                                                                       |
| ---------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 今回の構造検証   | オブジェクト、配列、必須項目、型、形式バージョン等を定義できる | 同様の要件を満たせる                                                          |
| 書き方           | 通常版はメソッドチェーンを中心とする                           | スキーマと関数、pipeを組み合わせる                                            |
| 型の導出         | スキーマからTypeScriptの型を導出できる                         | 同様に導出できる                                                              |
| 失敗の扱い       | safeParseで成功・失敗を受け取れる                              | safeParseで成功・失敗を受け取れる。abortEarlyで最初の問題で中止する構成も可能 |
| 未使用機能の削減 | 通常版に加え、関数型APIのZod Miniも選択肢                      | モジュール化を重視したAPI。使用する機能を絞りやすい                           |
| 今回の連携要件   | 他ツールとのZod連携を使う要件は現時点でない                    | 特定ツールとの連携を前提にしなくても使える                                    |

根拠は[Zodの基本API](https://zod.dev/basics)、[Zod Mini](https://zod.dev/packages/mini)、[Valibotの設計](https://valibot.dev/guides/mental-model/)、[Valibotのデータ検証](https://valibot.dev/guides/parse-data/)。どちらも画像ファイルの存在やデータ間の参照整合性を自動で保証するものではない。

既存コードの移行や特定連携に縛られず、両方の使用経験があるため、必要なスキーマ・関数で検証を構成できるValibotを選んだ。公開されているブラウザ向けのバンドル削減率を、このExpo/Metroアプリでの実測値として扱わない。Zodを選ぶ場合も、容量削減のためだけに慣れないMiniを自動採用しない。

両方の使用経験を踏まえ、Valibotの採用を確認済み。バックアップの構造検証という用途に絞り、必要なスキーマ・関数で構成できることを判断理由とする。追加パッケージ数がZodより減る、あるいはこのアプリで必ず高速・小容量になるとは主張しない。

### パスワード付きバックアップの選定結果

今回必要なのは、記録・ピン・写真・写真配置を一ファイルへまとめ、パスワードで保護してiPhoneとAndroid間で復元できること。既存データの置き換えと破損検証は、アーカイブライブラリとは別にアプリ側で設計する。

| 方式                                     | 利点                                                                     | 検討点                                                                                                                                          |
| ---------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| AES暗号化ZIPを扱うネイティブライブラリ   | ファイルをまとめる処理とパスワード保護を一つのライブラリへ任せられる候補 | 暗号方式の明示、両OS間の互換性、写真数千枚でのメモリ・作業領域・中断時の確認が必要                                                              |
| アーカイブ処理と暗号化を別に組み合わせる | 暗号化対象やコンテナ形式を細かく設計できる                               | パスワードからの鍵生成、暗号化・検証、大容量処理、形式の互換性を組み立てる範囲が増える。Expo Cryptoだけで完成したバックアップになるわけではない |

依存と独自実装を抑える観点から、AES暗号化ZIPを使う方向で進めることを確認済み。具体ライブラリはreact-native-zip-archiveを採用する方針を確認済み。旧式のSTANDARD/ZipCryptoを選ばず、AES方式を明示する。

候補の[react-native-zip-archive公式資料](https://github.com/mockingbot/react-native-zip-archive)には、iOS・Androidのパスワード付きZIPとフォルダ指定でのAES対応が記載されている。ファイル配列指定などはOSや版で対応が異なるため、APIの名前だけで同等と判断しない。Expo Goでは動かずDevelopment Buildが必要。ライブラリの採用方針は確認済み。具体的なバージョンは未確定。

#### ライブラリ候補の比較

| 候補                                                                               | 確認できた内容                                                                                                      | 今回の判断                                                                   |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| [react-native-zip-archive](https://github.com/mockingbot/react-native-zip-archive) | 両OSでの作成・復元、AES指定、進捗、一覧取得や中断等のAPIを持つ。Expo Development Buildに対応                        | 既存構成へZIP処理を加える第一候補。採用版のAPI・暗号化・必要な修正を確認する |
| [react-native-nitro-archive](https://github.com/mCodex/react-native-nitro-archive) | 両OSのAES-256、一覧・検証・展開制限等に対応すると記載。Nitro Modulesが必要で、公式READMEはpre-1.0として扱うよう明記 | 機能は合うが、新たな基盤依存とAPI変更リスクを追加する理由が現時点では弱い    |

比較後、react-native-zip-archiveを採用する方針をユーザーと確認済み。採用方針を決めても、iPhoneで作成してAndroidで復元する往復、大容量処理、誤パスワード・一部破損・中断時に既存データが保たれることを、実装段階で確認する必要がある。README上の対応を実機検証済みの事実として扱わない。

[公式リリース情報](https://github.com/mockingbot/react-native-zip-archive/releases)には書き出し完了や展開先の安全性に関する修正もあるため、採用時は修正の取り込みを確認する。内容検証前に既存記録へ展開せず、専用の作業領域に展開する。アーカイブ内のファイル名は識別子を基準とし、個人の文章や場所名を直接埋め込まない案。
